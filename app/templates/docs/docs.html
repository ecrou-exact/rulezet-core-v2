Request lifecycle

Every HTTP request flows through exactly four layers. Each layer has a single job — nothing leaks between them.

Route (<feature>.py)

Parses the incoming request, validates form data with form_to_dict(), calls a core function, then flashes a message and redirects. It never touches the database directly.

Core (<feature>_core.py)

Contains all ORM queries and business logic. Always returns a tuple (object, "message"). All log_action() calls live here.

API Resource (app/api/<feature>_api.py)

Flask-RESTX resource classes. They validate JSON input via a verification module, call the same core functions as the HTML routes, and return JSON.

Verification (verification_<feature>.py)

Pure input validation — no ORM, no side effects. Returns errors or a clean dict that the API resource can safely pass to core.

Routes never query the database. If you find yourself importing a model inside a route file, move that logic into the corresponding core file.
{# ════════════════════ LAYERS ════════════════════ #}

Layer responsibilities

Layer Allowed to do Never does
Route Parse request, call core, flash, redirect, render template ORM queries, log_action, business logic
Core ORM queries, business rules, log_action, return (obj, msg) Flash messages, redirects, HTTP concerns
API Resource Validate JSON, call core, return JSON response Direct ORM access, log_action (delegate to core)
Verification Validate types, ranges, formats, return errors Any database access, any side effect

    <feature>_core.py     ← all DB logic + log_action
    form.py               ← WTForms

Roles

Every user has exactly one Role. Roles carry two special flags and a set of granular permission keys.

FlagMeaning
admin Full unrestricted access. Bypasses all permission checks automatically. Use user.is_admin() to test.
read_only Restricts to safe HTTP methods (GET/HEAD). Use user.read_only() to test. Enforce in core functions when needed.
protected Role cannot be deleted through the UI. Set on seeded system roles.

Useful User methods

python 
user.is_admin()              # True if role.admin
user.read_only()             # True if role.read_only
user.has_permission('key')   # True if admin OR role holds that key
user.display_name()          # username or "First Last"
user.initials()              # "FL" — for avatars
user.full_name()             # "First Last"
user.to_json()               # safe serialisation dict

Permissions

Permissions are plain string keys stored in app/core/utils/permissions.py. Nav items are registered in app/core/utils/nav_registry.py — those are the only two files to touch when adding a feature's access rules.

Defining a permission key

Keys follow dot notation: feature.action. Add them in permissions.py as constants so they are autocompleted across the codebase.

permissions.py 
# add your feature block
INVOICE_VIEW   = 'invoice.view'
INVOICE_CREATE = 'invoice.create'
INVOICE_EDIT   = 'invoice.edit'
INVOICE_DELETE = 'invoice.delete'

Registering in nav_registry.py

nav_registry.py 
NAV_ITEMS = [
    ...
    {
        'label': 'Invoices',
        'icon':  'fa-file-invoice',
        'url':   'invoice.index',
        'permission': 'invoice.view',   # None = all auth, 'admin_only' = admins
    },
]
Never touch _nav.html or _search_sections.html. Both are generated automatically from nav_registry.py.
{# ════════════════════ DECORATORS ════════════════════ #}

Decorators

One decorator handles all access control for HTML routes. A matching decorator covers API resources. Never leave a route without one.

HTML routes — require_permission(key)

python 
from app.core.utils.decorators import require_permission

@blueprint.route('/invoices')
@require_permission()                   # any authenticated user
def index(): ...

@blueprint.route('/invoices/new')
@require_permission('invoice.create')   # requires that key (admins bypass)
def create(): ...

@blueprint.route('/admin/invoices')
@require_permission('admin_only')       # admin flag required
def admin_list(): ...

When the user is not authenticated, require_permission redirects to login automatically. On a permission mismatch it returns 403.

API resources — api_require_permission(key)

python 
from app.core.utils.decorators import api_require_permission

class InvoiceList(Resource):
    method_decorators = [api_require_permission('invoice.view')]

    def get(self): ...

class InvoiceAdmin(Resource):
    method_decorators = [api_require_permission('admin_only')]

    def delete(self, uid): ...

The API decorator accepts both X-API-KEY header (external clients) and session authentication (internal frontend calls). You never need to handle both manually.

Model conventions

Every new model must carry the full set of standard fields. This enables soft-delete, audit trails, and public/private visibility out of the box.

python — standard fields 
import uuid as _uuid
from datetime import datetime
from app import db

class Invoice(db.Model):
    # ── Identifiers ─────────────────────────────────
    id          = db.Column(db.Integer, primary_key=True)
    uuid        = db.Column(db.String(36), unique=True, nullable=False,
                            default=lambda: str(_uuid.uuid4()))

    # ── Content ─────────────────────────────────────
    title       = db.Column(db.String(255), nullable=False)
    description = db.Column(db.Text, nullable=True)
    is_public   = db.Column(db.Boolean, default=False)

    # ── Traceability ─────────────────────────────────
    created_at  = db.Column(db.DateTime, default=datetime.utcnow)
    updated_at  = db.Column(db.DateTime, default=datetime.utcnow,
                            onupdate=datetime.utcnow)
    created_by  = db.Column(db.Integer, db.ForeignKey('user.id'), nullable=True)

    # ── Soft delete ──────────────────────────────────
    is_active   = db.Column(db.Boolean, default=True)
    deleted_at  = db.Column(db.DateTime, nullable=True)
    deleted_by  = db.Column(db.Integer, db.ForeignKey('user.id'), nullable=True)

    # ── Flexible metadata ────────────────────────────
    meta        = db.Column(db.JSON, nullable=True)

    # ── Your feature fields below ────────────────────
    amount      = db.Column(db.Float, nullable=False)

Querying active vs trashed records

python 
# Active records (default view)
Invoice.query.filter_by(is_active=True).all()

# Trash (admin restore / hard-delete view)
Invoice.query.filter_by(is_active=False).all()

# Accept both ID and UUID in routes
from app.core.utils.utils import isUUID

def get_invoice_or_404(uid):
    if isUUID(uid):
        return Invoice.query.filter_by(uuid=uid, is_active=True).first_or_404()
    return Invoice.query.filter_by(id=uid, is_active=True).first_or_404()

Deletion pattern

User actions never physically delete a row. Hard deletion is an admin-only operation, accessible exclusively from the trash view at /admin/<feature>/trash.

python — core 
from datetime import datetime
from flask_login import current_user

def delete_invoice(invoice):
    """Soft delete — called from a user action."""
    invoice.is_active  = False
    invoice.deleted_at = datetime.utcnow()
    invoice.deleted_by = current_user.id
    db.session.commit()
    log_action("Invoice deleted", "delete", ...)
    return invoice, "Invoice moved to trash."

def restore_invoice(invoice):
    """Restore from trash — admin only."""
    invoice.is_active  = True
    invoice.deleted_at = None
    invoice.deleted_by = None
    db.session.commit()
    log_action("Invoice restored", "restore", ...)
    return invoice, "Invoice restored."

def hard_delete_invoice(invoice):
    """Permanently destroy — admin, from trash only."""
    db.session.delete(invoice)
    db.session.commit()
    log_action("Invoice permanently deleted", "hard_delete", ...)
    return None, "Invoice permanently deleted."

Core functions

Every core function returns a two-tuple (result, message). The route or API resource decides what to do with both values — core has no opinion about HTTP.

python — core 
def create_invoice(data: dict):
    """data comes from form_to_dict() or verified API payload."""
    invoice = Invoice(
        title=data['title'],
        amount=data['amount'],
        created_by=current_user.id,
    )
    db.session.add(invoice)
    db.session.commit()
    log_action("Invoice created", "create", category="invoice",
               level="success", object_type="invoice",
               object_id=invoice.id, is_public=True)
    return invoice, "Invoice created successfully."
python — route consuming core 
@invoice_blueprint.route('/new', methods=['POST'])
@require_permission('invoice.create')
def create():
    form = InvoiceForm()
    if form.validate_on_submit():
        data = form_to_dict(form)
        invoice, msg = create_invoice(data)
        flash(msg, 'success')
        return redirect(url_for('invoice.detail', uid=invoice.uuid))
    return render_template('invoice/create.html', form=form)

log_action()

The central logging helper. Call it exclusively from *_core.py files. It never raises — a logging failure cannot break a request. The actor, IP address, and user-agent are detected automatically from the request context.

python — signature 
from app.core.utils.logger import log_action

log_action(
    title="Invoice created",      # required — human-readable summary
    action="create",              # required — machine key
    category="invoice",           # user|system|security|admin|api
    level="success",              # info|success|warning|error
    description="Optional long text about what happened",
    object_type="invoice",        # the model being acted on
    object_id=invoice.id,         # coerced to str automatically
    is_public=True,               # False = admin-only in log viewer
    meta={"role_id": user.role_id},  # IDs only — never plain names
    actor_id=None,                # override auto-detected current_user
)
Never put plain names or sensitive values (passwords, tokens, emails) in meta. Store IDs only. Names change; IDs don't, and they can be resolved at display time.

API category helper

Inside *_api.py files use api_category() when you want to distinguish external API calls (with X-API-KEY) from internal frontend calls.

JS conventions

All frontend code uses Vue 3 Composition API with ES modules. Templates use [[ ]] delimiters so Jinja2 and Vue don't collide.

App bootstrap

javascript 
const { createApp, ref, computed, onMounted } = Vue
import { TOAST, apiFetch }          from '/static/js/constants.js'
import { create_message, message_list } from '/static/js/toaster.js'
import LoadingBar  from '/static/js/components/loading-bar.js'
import Pagination  from '/static/js/components/pagination/pagination.js'

createApp({
    delimiters: ['[[', ']]'],
    components: { LoadingBar, Pagination },
    setup() {
        const page_is_loading = ref(false)

        onMounted(async () => {
            await Promise.all([fetchItems()])
            page_is_loading.value = true
        })

        return { page_is_loading, message_list }
    }
}).mount('#main-container')

Jinja values in scripts

Always quote Jinja expressions inside <script> tags to produce valid JS strings.

javascript 
{% raw %}// Correct
const userId   = '{{ current_user.id }}'
const userName = '{{ current_user.display_name() | e }}'

// Wrong — breaks if value contains quotes or special chars
const userId = {{ current_user.id }}{% endraw %}
Never use console.log. Never use display_toast() directly in templates — always create_message().

Toasts

create_message() is the single way to show feedback to the user from JavaScript. Use TOAST.* constants — never raw strings.

javascript 
import { TOAST, apiFetch }            from '/static/js/constants.js'
import { create_message }            from '/static/js/toaster.js'

async function saveInvoice() {
    const res = await apiFetch('/api/invoice/', 'POST', { title: 'Q1' })
    if (res.ok) {
        create_message('Invoice saved.', TOAST.SUCCESS)
    } else {
        const err = await res.json()
        create_message(err.message || 'Something went wrong.', TOAST.ERROR)
    }
}

// Sticky toast — stays until the user dismisses it
create_message('Import running in the background…', TOAST.INFO, true)
ConstantValueVisual
TOAST.SUCCESS'success'Green checkmark
TOAST.WARNING'warning'Amber triangle
TOAST.ERROR'danger'Red cross
TOAST.INFO'info'Blue circle-i

apiFetch()

apiFetch(url, method, body) is the only way to make API calls from the frontend. It automatically injects the CSRF token, sets JSON content-type, and returns a native Response.

javascript 
import { apiFetch } from '/static/js/constants.js'

// GET — no body
const res = await apiFetch('/api/invoice/123')

// POST with body
const res = await apiFetch('/api/invoice/', 'POST', {
    title: 'Q2 Invoice',
    amount: 4200,
})

// DELETE
const res = await apiFetch(`/api/invoice/${id}`, 'DELETE')

// Always check res.ok before consuming the body
if (!res.ok) {
    const err = await res.json()
    create_message(err.message, TOAST.ERROR)
    return
}
const data = await res.json()

DataTable

The <data-table> component is the only way to render tabular data. Never build a raw HTML table for listing records.

javascript — setup 
import DataTable from '/static/js/components/table/data-table.js'

const columns = [
    { key: 'title',  label: 'Title',  sortable: true },
    { key: 'amount', label: 'Amount', sortable: true },
    { key: 'status', label: 'Status' },
]
const items        = ref([])
const totalItems   = ref(0)
const currentPage  = ref(1)
const totalPages   = ref(1)
const allItemsIds  = ref([])  // for "select all pages"

async function fetchItems() {
    const res  = await apiFetch(`/api/invoice/?page=${currentPage.value}`)
    const data = await res.json()
    items.value      = data.items
    totalItems.value = data.total
    totalPages.value = data.pages
}

CSS conventions

One file per feature

Place feature styles in static/css/<feature>/<feature>.css and load it via {% block head_extra %}. Never add feature-specific rules to core.css.

Class naming

Always prefix classes with the feature name to avoid collisions. Use kebab-case.

css 
/* Good */
.invoice-card { ... }
.invoice-amount-badge { ... }

/* Wrong — no prefix, will collide */
.card { ... }
.badge { ... }

Section delimiters

Divide each CSS file into named sections for readability.

css 
/*---INVOICE_CARD---*/

.invoice-card { ... }

/*---INVOICE_TABLE---*/

.invoice-table-row { ... }

Dark mode

Override token-based styles with a [data-bs-theme="dark"] block. Anything referencing only CSS variables is automatically dark-mode compatible without extra work.

css 
[data-bs-theme="dark"] .invoice-card {
    box-shadow: var(--shadow-md);  /* shadow-md is already dark-aware */
}

/* Avoid hardcoded overrides — use tokens */
[data-bs-theme="dark"] .invoice-card {
    background: #1a1a1a;  /* Wrong — hardcoded */
    background: var(--bg-surface);  /* Correct */
}

New feature checklist

Every feature must pass all nine blocks before it is considered done. No exceptions.

1 — Structure

Create app/features/<f>/ with __init__.py, <f>.py, <f>_core.py, and form.py. Create app/api/<f>_api.py and verification_<f>.py. Add a CSS file and a tests folder.

2 — Model

All standard fields must be present. Run ./launch.sh --migrate "add invoice" then ./launch.sh --upgrade.

3 — Access

Add permission keys to permissions.py. Register nav items in nav_registry.py. Decorate every route and API resource.

4 — CRUD

HTML routes for list, detail, create, edit, delete. API endpoints for GET, POST, PUT, DELETE, restore, hard-delete, and bulk operations. Trash route at /admin/<f>/trash.

5 — Logs

Call log_action() on every mutating operation: create, edit, delete, restore, hard_delete, every bulk action, and any sensitive read.

6 — Background jobs

Any operation that touches more than 50 records or takes longer than 2 seconds must run as a background job. The API endpoint returns 202 + job_id. The frontend polls /api/jobs/<id>.

7 — Tests

Cover HTML routes (200 / 302 / 403 / 404 per role), API endpoints (201 / 400 / 403 / 404), the full trash flow (delete → restore → hard delete), and security-sensitive fields. Run ./launch.sh --test before declaring done.

8 — Docs & 9 — Security

Update CLAUDE.md and README.md. Run bandit -r app/ — no HIGH or MEDIUM findings. Ensure no sensitive data leaks through API responses or log entries.
